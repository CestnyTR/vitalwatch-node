# Changelog

> **Rename:** the package was renamed to VitalWatch — npm package
> `vitalwatch-node`, diagnostic command `vitalwatch-status`, environment
> variables `VITALWATCH_*`, signature headers `X-VitalWatch-Signature` /
> `X-VitalWatch-Timestamp`. The history below uses the new names.

Semver. In `0.x` releases **a minor bump counts as breaking**, so
`npm update` will not move from 0.3 to 0.4 and reports "up to date". To upgrade:

```bash
npm install vitalwatch-node@latest
```

## 0.5.3

### Changed

- Docs: README, CHANGELOG and package description are now in English.
- All user-visible output (CLI, log warnings, IDE docs) is now in English:
  `vitalwatch-status` labels and messages, and the JSDoc in `types/*.d.ts`
  shown by IntelliSense. Exit codes and output layout are unchanged.
- **One-time fingerprint change:** two event messages the SDK generates itself
  are now English — the worker/child-process exit error
  (`Worker exited with code 1`, `Child process exited with code 1 (SIGTERM)`)
  and the `vitalwatch-status --test` event
  (`Test event generated by vitalwatch-status --test`). The hub groups these
  under a new fingerprint once; the old Turkish rows stop receiving events
  and can be resolved. Slow request / `http_5xx` messages were already
  language-neutral and are unchanged.

## 0.5.2

### Changed

- **Plain CamelCase names are no longer masked as `[token]`.** The long-string
  mask (24+ characters) also treated class and method names such as
  `InvalidOperationException` and `HandleNonSuccessAndDebuggerNotification`
  as tokens, making stack traces unreadable. A candidate with no digits, no
  `-`/`_`, that fully matches `^[A-Za-z][a-z]+(?:[A-Z][a-z]+)+$` is no longer
  considered a token. Real tokens and session IDs almost always contain
  digits; strings with digits, consecutive capitals or all caps are still
  masked as before. The rule is identical in the hub, `t.js` and the other
  SDKs.
- **Fingerprint side effect:** error messages containing such a name are
  grouped under a new fingerprint once after upgrading; a new row appears in
  the panel and a one-time "new error" alert may fire.

## 0.5.1

### Fixed

- **The zero-code setup lost the mount path.** `auto.js` read the path from
  `req.url` when the response finished; Express strips the mount path from
  `req.url` when entering a mounted router. `/api/products` under
  `app.use('/api', router)` showed up in the panel as `/products`, and
  routers mounted under different prefixes collapsed into one record. The
  path is now captured at the start of the request (`originalUrl` if
  present). The Express adapter (`vitalwatch.express()`) was not affected;
  it already uses `baseUrl` + `originalUrl`.

## 0.5.0

### Added

- **The release tag is detected automatically.** `VITALWATCH_RELEASE` was set
  in almost no project, so the hub could not say "this error started after
  deploy X". Order: `VITALWATCH_RELEASE` > CI/PaaS variables (`GIT_COMMIT`,
  `GIT_SHA`, `COMMIT_SHA`, `SOURCE_VERSION`, `VERCEL_GIT_COMMIT_SHA`,
  `RENDER_GIT_COMMIT`, `HEROKU_SLUG_COMMIT`, `CI_COMMIT_SHA`) > `.git` in
  the application root (HEAD, branch ref, `packed-refs`, detached HEAD,
  `gitdir:` file). The sha is the first 12 characters, lowercased. Since
  deploys are a `git pull`, `.git` is in place; when the process restarts the
  new sha is read, and if it does not, old code is still running and the old
  sha is correct. `git` is never executed — only a synchronous file read at
  startup; it never throws. Same rule as Laravel and Python.
  `vitalwatch-status` shows the tag with its source.
- **Update check in `vitalwatch-status`.** Shows the latest version on npm;
  if it is newer than the installed one, prints the warning
  `Update available: npm install vitalwatch-node@latest`.
  Does not change the exit code; if npm is unreachable it prints
  `could not check`. `VITALWATCH_STATUS_OFFLINE=1` skips it.
  Only in the diagnostic command — no npm requests at runtime.
- **Environment name normalization.** The hub accepts only
  production/staging/local and drops anything else — heartbeats included —
  with a 204. A project set up with `NODE_ENV=development` or `prod` looked
  as if it sent nothing. Aliases are mapped (`prod`/`live`,
  `stage`/`stg`/`preprod`/`uat`, `dev`/`development`/`test`/`testing`); an
  unrecognized value is sent as-is and the diagnostic command reports an
  error. The table is the same in all three packages.
- **Framework adapters:** Nuxt (module), Nitro, Fastify, Koa, Hono, NestJS,
  SvelteKit, React Router 7 / Remix.

  These frameworks catch handler errors internally and turn them into a
  response; the zero-code setup only saw "HTTP 500" and the error class and
  stack were lost. The adapter sends the error itself. 4xx is not sent.

  Adapters with access to the response object (Nuxt/Nitro, Fastify, Koa,
  Hono-Node, NestJS-HTTP) mark the response, so the zero-code setup does not
  open a separate "HTTP 500" for the same request. **SvelteKit, React Router /
  Remix and Next cannot set the mark** (the hook only exposes the web
  `Request`): if the zero-code setup is also loaded, one failure produces two
  records — `exception` and `http_5xx`.

  Hono is supported only on Node (`@hono/node-server`) and Bun; Workers/edge
  are not supported (`node:fs`/`node:crypto`, no `waitUntil`).

  In NestJS non-HTTP contexts (`rpc`, `ws`), `RpcException` /
  `WsException` and their subclasses are not sent: they are business errors
  returned to the client.

  If the application turns an error without a status code into a 4xx in its
  own handler (Fastify `setErrorHandler`, a Nest filter), the error is still
  sent; the adapter cannot foresee that decision.

  Route naming matches the zero-code setup: `/games/earthquake-kit` stays
  as-is, only numbers / UUIDs / long hex are replaced.

  Tested end to end against real versions: Nuxt 3.21.11, Fastify 5.12,
  Koa 3.2, Hono + @hono/node-server, NestJS. The Nuxt run caught three bugs,
  all fixed: Nuxt silently replaced the CommonJS app plugin with an empty
  function (an ESM gate was added); every error showed up as `Error` because
  the h3 wrapper has no name (now recognized by a static marker); and SSR
  errors were sent twice because the package was bundled into two build
  outputs (the mark now lives on the error object, via a global symbol).

- **`report(error, { res })`.** If an application with its own error handler
  passes `res`, timing does not open an "HTTP 500" for the same request. In
  gyd-backend every 5xx was two records in the panel: one sent by
  `errorHandler` and one opened by the timing middleware. The mark is set
  only if the error will actually be sent (new `Reporter#willRecord`): for an
  ignored class, or the second pass of a single error object thrown on every
  request, the "HTTP 500" remains the only trace.
- **Types:** `nitro.d.ts` / `nuxt.d.ts` (`export =` — verified by compiling
  with `moduleResolution` `node16` and `bundler`), `ReportContext` (`res`
  only in `report()`), `Reporter#willRecord`.
- **`startHeartbeat` / `stopHeartbeat` types.** They existed at runtime since
  0.4.0 but were missing from `types/index.d.ts`; TypeScript projects had to
  write their own declarations.

### Changed

- **`vitalwatch.errors()` no longer sends 4xx.** Same rule as the other
  adapters. Previously every error was sent and validation errors flooded the
  panel for public APIs; gyd-backend never used the middleware for that
  reason.

### Fixed

- **`VITALWATCH_TIMEOUT=2` cut sending off after 2 ms.** Laravel and Python
  expect seconds under the same name; an installation that copied the same
  value delivered no events at all — silently. Values below 100 are now
  treated as seconds; the result is clamped to 100–10000 ms, and invalid /
  zero / negative / infinite values fall back to 2000 ms. The rule is shared
  by all packages and also applies to `init({ timeout })`.
- **`ignore: ['Name']` dropped every other error.** `instanceof` was applied
  to the string in the list, a TypeError was thrown and `recordException`
  gave up: no error with a non-matching name was ever sent. `instanceof` is
  now applied only to class entries.
- **`vitalwatch.errors()` could call `next` twice.** In the 4xx branch `next`
  was inside the try; if it threw synchronously, the catch swallowed it and
  the flow fell through to a second `next(error)`. Now there is a single
  call, outside the try.
- **Masking mangled readable names.** Upload file names now stay readable.
  Names like `<name>-<timestamp>-<random>.jpeg` showed up in the panel as
  `/uploads/discount/[token][card]-752066249.jpeg`: the timestamp was taken
  for a card number and the long name for a token.

  - **Card:** only digit strings starting with 2–9 that pass Luhn are masked;
    millisecond timestamps start with 1. Deliberate trade-off: mistyped
    (non-Luhn) card numbers and UATP cards starting with 1 are no longer
    masked.
  - **Token:** hex strings containing a 16+ character unbroken segment or
    letters (UUIDs, hashes) are masked. Short segments joined by hyphens are
    a readable name. Deliberate trade-off: random keys split by hyphens or
    underscores into segments shorter than 16 characters (some base64url
    tokens, `AIza…`-style keys) may pass unmasked.
  - **Phone:** does not match when preceded by a digit. A timestamp whose
    last ten digits started with 5 became `179[phone]`. The `90` country code
    written without a leading `+` (`905321234567`) is now also recognized —
    the first version of this rule left that format unmasked.

  The rules are identical in the hub, `t.js`, Node, Laravel and Python;
  compared against 28 shared vectors.
- **One failure produced two records.** Express's `errors()` middleware sent
  the error, and the timing middleware opened another stack-less "HTTP 500"
  for the same request. The response is now marked; timing and the zero-code
  setup do not open a 5xx record for a marked request.
- **Named imports from ESM did not work.** `import {
  nextOnRequestError } from 'vitalwatch-node'` failed in plain Node ESM with
  "Named export not found": exports used the `key: require(...)` form, which
  Node cannot detect statically. The Next bundler was hiding this.

## 0.4.2

### Fixed

- **Express: the mount path was not included in the route pattern.** An
  endpoint under `app.use('/api', router)` was reported as `/products/:id`
  instead of `/api/products/:id`.

  The result was a silent grouping bug: two routers mounted under different
  prefixes collapsed into one record. `/api/products/:id` and
  `/admin/products/:id` became a single row in the panel, error counts were
  summed and endpoint percentiles mixed two separate endpoints.

  The condition was inverted: if `req.route.path` was set it short-circuited
  and returned it alone; the branch that prepended the mount path only ran
  when `route.path` was EMPTY — i.e. when there was nothing to prepend to.

### Added

- **Tests for `src/express.js` and `src/next.js`.** Both files were installed
  in client projects and had no tests at all; the bug above surfaced while
  closing that gap.

  22 tests: route pattern, mount path, query string scrubbing (M3), 5xx
  marking, no timing record on client disconnect, errors not swallowed, and
  the request being unaffected when the reporter blows up. All four of four
  mutations are caught.

## 0.4.1

### Added

- **`vitalwatch-status --vitalwatch`** — tests the connection without
  dropping an error into the panel.

  `--test` sends a real exception and is the right choice when verifying a
  single installation: transport and scrubbing are exercised together. But
  in an update loop that walks dozens of installations it leaves dozens of
  fake errors in the panel — the monitoring tool producing its own noise.

  `--vitalwatch` carries no events; when accepted, it refreshes the
  project's connection status. HTTP 204 is still not proof of acceptance
  (the endpoint returns 204 for an invalid signature too), but real proof
  now lives in the panel: the connection shows `Connected`.

## 0.4.0

**Hub requirement:** for the hub to recognize this version's heartbeat, the
migration adding the liveness columns to the `vw_projects` table must be
applied. Upgrading without it does no harm — the heartbeat is accepted, just
not recorded.

### Added

- **Liveness heartbeat.** Every eight hours a request with no events is sent
  (`{"events": []}`). The hub used to infer that an installation worked only
  from incoming errors; an application running without errors looked like a
  "broken installation". The request itself is now the proof.

  The interval is one third of the hub's 24-hour silence threshold, so a
  single missed request — a deploy, a restart — does not make the
  installation look broken.

  Starts automatically with `hookProcess()`. `startHeartbeat` and
  `stopHeartbeat` are exported for manual control. The timer is `unref`'d;
  it does not keep short-lived scripts alive.

- **Worker thread and `fork()` crashes.** `hookProcess()` only hooked the
  main thread; an error thrown inside a worker left no trace. Uncaught errors
  and non-zero exit codes are now reported.

  `spawn`/`exec` are deliberately out of scope: a non-zero exit code is
  routine for external commands, and counting it as an error would flood the
  panel with meaningless records.

### Fixed

- `npm test` did not run at all on Node 24: `node --test test/` treated the
  directory as a module and failed. 33 tests were invisible.
